# Release plan v0.2.11

> Release plans list the stories a release takes from several epics. The epics stay organised by topic; status lives in [FEATURES.md](../FEATURES.md) and in each epic file.
>
> Previous release: v0.2.10 (clearer views of past and present work).

**Theme:** Spec Kit as an alternative to AI-DLC: the app sees which framework a project has, lets the person choose or switch, and follows and drives Spec Kit projects with their own views. Also: one committer per feature-doc change, and commit subjects that name only the stories that changed.

**Baseline (2026-11-19):** Planned the same day as EPIC-14 was written, after a look at Spec Kit v1.4.2. Nothing in it is built. Today the app opens only folders with `aidlc/spaces/` (`detectProject` in `src/main/projectService.js`).

## Build order

The order follows the theme: each story should make the ones after it cheaper or safer to build. First the two fixes, because every later story changes the feature docs. Then the framework seam, then reading Spec Kit (where the unknowns are), and last the stories that write: setup, choice and switch.

| # | Story | AI-DLC plan | Why here |
|---|-------|-------------|----------|
| 1 | **US-0032** one committer | quick-fix | Every later story edits the feature docs. With the rule on, agents stop racing the app for those commits from story 2 on. |
| 2 | **US-0033** commit subjects | quick-fix | The rest of the release then has a history that says which story each docs commit changed. Small, in `src/main/parsers/features.js` and `subjectOf`. |
| 3 | **US-1401** framework seam | express | The one change to code every view depends on: `detectProject`, the project settings and the left arm. Worth a design step. AI-DLC projects must behave exactly as today, and the existing suite proves it. |
| 4 | **US-1402** Spec Kit features | express | The largest unknown: Spec Kit's file formats. Starts with a test project made by hand with `specify init` (story note), which also becomes the test fixture for 5–9. Its design decides the parser's shapes. |
| 5 | **US-1403** run commands | ultra-express | Needs where a feature stands (4) to offer the next command. Reuses the terminal and quick commands from EPIC-05. |
| 6 | **US-1404** constitution and extensions | ultra-express | Small and read-only. Its extensions list also feeds the quick commands of 5. |
| 7 | **US-1405** Spec Kit setup | ultra-express | The first story that writes into a project. Mirrors US-0503's preview-then-run. |
| 8 | **US-1406** detect and choose | ultra-express | Brings 3 and 7 together at the first open: what is found, and the choice. |
| 9 | **US-1407** switch | ultra-express | Last, because it uses all of the above: setup (7), the saved choice (8) and both view sets (3–6). |

**Until US-1406 (stories 3–7):** the app follows what it finds. A folder with only `.specify/` opens as Spec Kit. A folder with both opens as AI-DLC, as today. US-1406 then replaces this rule with the person's choice.

**Before story 4:** the `specify` CLI is installed on the build machine (`uv tool install specify-cli`), at the version the stories were written against (v1.4.2) or newer, and the version is noted in the fixture.

**Working rules for the release:**
- One story at a time, in this order. Two stories from the same `main` mean merging `main` in and running the whole suite again (project rule), which is waste.
- A fresh session after each stage. During the TDD loop run only the test being worked on; the full suite runs once before Build and Test is approved, and in CI.
- From story 2 on, agents on `main` leave feature-doc commits to the app (US-0032).
